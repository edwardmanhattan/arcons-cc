Architecture III: the picture, from wire to pixel

The wall gets the fleet by two transports. It builds one model from both. The map thread draws the water. The marker layer projects each hull with the frame that the map thread drew.

Code: src/data/types.rs, src/units/, src/map/, src/ui/markers.rs, src/live/wire.rs. Diagrams rendered with Pele.

Overview Runtime Picture Control Verification

Two transports, one model

The wall uses HTTPS for the standing picture and WSS for movement. The standing read is the authority for membership and for age. The socket is an accelerator over that read. It is not a second truth.

The standing read

One read returns every hull. A hull can have no position. That is a normal value, not an error. The type keeps the difference between "not measured" and "zero" (INV-01).

The model replaces its whole unit list from this read. Membership belongs to the server. If a hull is absent from the read, the hull is absent from the fleet. The model does not keep a hull that the server removed.

UnitView::silent sets position: None. A silent hull is in the picture and not on the map. This is the common case on the development feed: 126 of 127 hulls have no fix.

The live fix

A live publication is flat. The three optional measurements are absent when unmeasured. The backfilled flag travels with the fix. The socket type is separate from the HTTP type because the wire shapes are different.

Picture::apply_fix finds the hull by id_unit. If the hull exists, the fix updates the position and the measured values. If the hull does not exist, the fix adds the hull. The socket is allowed to know about a hull that the last read did not have.

A read is a snapshot

A fix from the standing read has travel: None. The marker appears where the server puts it. It does not fly there from its old position. On a reconnect, a flight across the sea would show a movement that did not occur.

Age, glyphs, and absence

The server sends age_seconds at read time. The wall stores that value with the receipt time. Between reads, the wall adds the monotonic elapsed time. The wall never compares a server timestamp with the local clock (INV-06).

The deployment can change the threshold with stale_after_s in config.toml. The code default is 120 s. The threshold is a client decision because the server does not know what the operator is looking at.

Movement is a drawing decision

A hull that moves 200 m between reports should move on the wall. The marker travels from the old drawn position to the new fix over 600 ms. The travel is a display value. It never changes the fix (INV-05).

The three refusals are important. A backfilled fix must not slide into place. A large jump must not look like a fast ship. A fix after a long silence must not draw a course that nobody observed.

The map thread and the offline seed

The map engine is MapLibre Native. It runs behind the map feature. The gate does not build it, because the gate must need no C++ compiler, no network, and no GPU. CI compiles it on macOS. The wall builds it with scripts/build-wall.sh.

The seed is a 2.6 MB SQLite cache. It is embedded in the binary with include_bytes!. On the first start, the map thread copies the seed to a writable cache. It pins the expiry of every row to the year 2100. Without this step, MapLibre tries to revalidate the style over the network. On a wall with no network, the map would stay black.

prepare_cache does three jobs. It sets a corrupt cache aside. It copies the embedded seed when the cache is absent. It runs UPDATE resources SET expires = ? and UPDATE tiles SET expires = ? on every start. The last job is why an old cache stays offline-usable.

The renderer is a Continuous renderer. The thread builds it one time and keeps it. The GL context, the tile cache, the glyph atlas, and the shaders stay hot. A camera change then costs milliseconds. A new renderer would cost seconds.

The first frame

The renderer pumps a number of frames after the style loads, so the first frame that reaches the view loop has tiles. A first frame with no tiles is a grey rectangle. The log line first map frame in … ms is the measured number.

One projection

The map and the markers must agree on where a latitude and longitude land. They agree because there is one function. Both call map::geometry::project with the camera of the rendered frame. There is no second conversion (INV-04).

The world is 512 pixels at zoom 0. MapLibre uses this convention. A 256-pixel base would put every marker at half of the offset that the map draws. The error is small at zoom 3 and large at zoom 11.

Markers use the frame's camera, not the pane's live camera. Mid-gesture, these two cameras differ. The picture on screen is the old frame. A marker that used the new camera would move before the water moves.

Markers

The marker layer is a pure function. It takes the picture, one rendered frame, and one pane's filter. It returns one placed marker for each hull that has a fix.

The filter belongs to the pane. A pane that hides the hull layer gets no markers from this function. There is no second place where “hulls are off” can be forgotten.

The glyph can be 12 points. The hit target is at least 24 points. A touch target is a decision about fingers, not about the size of the symbol. At a high zoom, a hull with a picture can draw the picture instead of the symbol. The switch uses the pane's frame zoom, not the camera, so a hull does not change representation while it is still projected against the old frame.

Cards and pane state

The data is shared. The question is not. The wall has one picture and one socket. Each pane has its own selection, its own card, its own filter, and its own symbol-or-picture range.

A press in one pane changes that pane. It does not change a neighbour. This rule is INV-10. The first version had one wall-wide selection, and it drew the same card in every pane.

A card is built from the picture. If the hull moves, the card follows. The card also uses the reads thread for the hull's identity, commander, and specifications. Those reads use the same Command and Reply channel as every other REST read.

The socket envelope is not uniform

Centrifugo adds one data level. The channels below that level have different shapes. A client that assumes one shape reads undefined and gets no error. The parser refuses the wrong shape.

channelshape under pubparser

game:<id>:positionsdata.positions, no typenot this client

The caller passes the bytes of pub.data, not the whole envelope. The data level belongs to the transport. If two places unwrap it, the two places will disagree about the depth.
