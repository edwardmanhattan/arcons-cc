Architecture II: the wall's runtime

The wall is one window and several threads. The view loop owns the state. The other threads do slow work and send messages. This page shows the start order, the channels, one frame, and the stop order.

The start order

The start order is deliberate. A flag must answer before the program touches the network. The log must start before the program writes a line. The GPU pin must happen before Rune starts a thread. The configuration is read before the window opens.

  1. Parse the command line. --help and --version return here.
  2. Start the log. Every later line also goes to the log file.
  3. Pin the Vulkan device. The loader reads the environment one time.
  4. Read config.toml and the credential. --self-check returns here.
  5. Install the SIGTERM handler. A stop during startup is not lost.
  6. Open the window. Rune calls setup, then poll and view for each frame.
Why the order matters

pin_gpu_from_env changes VK_DRIVER_FILES and VK_ICD_FILENAMES. The Vulkan loader reads these variables one time. A call after Rune's threads start would not move the map to the compositor's GPU.

Rune's application contract

Rune owns the event loop, the window, and the GPU surface. The application gives Rune four functions and one scene list. The functions are small. The work is in the threads that feed them.

view is a pure function of State. It builds an El tree and returns. It does not read the network, wait for a thread, or write a file. State changes only on the view loop's thread. poll drains worker messages and applies them. Input handlers apply intents on the same thread.

The threads and the channels

There are four kinds of worker thread. They do not share mutable domain state. They send values to the view loop. The view loop is the only writer of State.

One exception, and it is safe

The map thread writes pixels through rune::Pixels::set. That function is made for a call from another thread and merges writes between frames. The map thread also writes one Rendered value behind a mutex. Both are handover slots, not domain state.

Example: the reads thread

The reads thread does the HTTPS work. It signs in one time and refreshes the token at 80% of its stated life. A request is an enum value. A reply is an enum value. The view loop sends a request and continues. It reads the reply on a later frame.

The handle has two methods. Both are non-blocking. request never waits for the network. try_recv never waits for an answer.

One current-thread Tokio runtime per worker is a decision about isolation. The reads thread and the socket thread each own a runtime. A slow read cannot take a worker from the socket. The cost is no work stealing. The workload is a small number of routes, so the cost does not matter.

Example: the socket thread

The socket thread owns one Centrifugo connection for each attempt. It sends an Update for each fact that the view loop needs. It also calls a wake function after each update, so Rune draws the new picture now and not on the next idle frame.

The actor has a fixed loop. The loop is short because each extra branch is another state to get wrong. The reconnect sequence is the important part. A socket connect is not a current picture. live-feed has no history. After a connect, the actor reads the whole picture and then subscribes. Until that read completes, the header says reconnecting (INV-09).

The backoff is exponential and fully jittered. The bound is 1 s, 2 s, 4 s, and so on to 30 s. The wait is a random value between zero and the bound. A fleet of walls must not reconnect in one millisecond after a server restart.

One frame

Rune calls poll before it calls view. poll drains every channel. It applies each value to State. It reports whether a pixel changed. view then builds the element tree from the new state.

The socket drain is a good example. It collects the updates first, then applies them. This order ends the borrow of state.live before apply_update needs the whole state mutably.

The order inside apply_update follows the facts. A Picture makes the wall live. A Fix moves one hull. Connected, Untrusted, RefreshDue, and Retrying do not make a picture current. They only change the header.

How a map frame crosses to the view loop

A map pane has a thread. The thread owns the MapLibre scene, the tile cache, the glyph atlas, and the GL context. It receives camera and size requests. It sends two values back:

  • RGBA pixels, through rune::Pixels::set;
  • one Rendered value with the camera and the frame size.

The thread merges requests. A drag sends one camera for each frame. The thread drains the queue before it renders. The newest camera wins. This rule keeps a fast drag from building a queue of frames that nobody sees.

A map thread starts after the first layout pass, because the pane's size is known then. A restored wall, a moved pane, and a new pane all use State::spawn_missing_maps. One function starts a thread for every pane that has no thread. That one function is why a restored pane cannot come back as a blank map.

The stop order

SIGTERM sets a flag. poll sees the flag and calls stop. The order is three steps. The order is the part that makes a clean stop clean.

  1. Write the arrangement. A SIGTERM one second after a split keeps the split. The write completes before the deadline starts.
  2. Arm the deadline. platform::QUIT_DEADLINE is 5 s. If the quit is still running, Rune writes the step it reached, marks quit.deadline, and ends the process.
  3. Join the map threads. Each map thread owns a GL context. MapLibre aborts if the process drops a context under a live render. The join gives each thread its ordered stop.

The unit file sets TimeoutStopSec=10. The deadline is 5 s. The gap is deliberate. If systemd sent SIGKILL first, the log would not say which step hung.

Headless mode is a different setup

A capture is not a wall. rune::is_headless() is true for --scene, --snap, --tree, and --script. In that mode:

  • no control socket opens;
  • no relay dials;
  • no Minos read starts;
  • no map thread starts;
  • the logical clock starts at zero and moves only by the capture's --at value;
  • one map pane gets a synthetic frame from its laid-out rectangle.

These rules make a capture independent of the machine, the network, and the wall clock (INV-11). A capture that opened a socket would fail on a build machine with no deployment.
