Architecture IV: control, fleet, and files

The wall has one door for every input. Local clients and remote clients use the same vocabulary. One queue holds their requests. The view loop applies them in arrival order. This page shows the door, the carriers, the viewer, the relay, and the files the wall writes.

Code: src/control/, src/control/sessions.rs, src/control/authority.rs, src/config/layout.rs, crates/desk. Diagrams rendered with Pele.

One door for every input

A pointer event, a key, a command-line client, a phone, and a scene script all end at the same function. The function is control::apply. It takes an Intent and a State. It returns one of three results: a change, a pairing, or a refusal.

An intent is a settled change. A pan is not sixty intents. The client computes the final camera and sends one Camera value when the hand stops. A wall that applied sixty intents a second would make its state equal to its input rate.

A refusal is a name. It is not silence, and it is not a default. The name comes from the same rule that the visible control uses. For example, ClosePane asks State::can_close. The menu row is built from that same predicate. The two cannot disagree.

Refusal categories

A refusal carries a category: rule, version, input, or busy. A client chooses between retry, fix the call, or update the app. It does not read a sentence to decide (INV-07).

Carriers and one queue

A carrier is a transport that carries JSON lines. The unix socket is one carrier. The relay is another. A carrier parses a line and makes a Job. It does not change the wall. The job goes into the wall's one queue. The view loop drains that queue between frames.

A Job is a request or a departure. A request has a reply channel, so the carrier can answer the client without touching State. A departure says that a hand is gone. Its cursor goes with it.

The listener binds the socket before it starts its thread. The socket is mode 0600, inside a directory that is mode 0700. The directory closes the time between bind and set_permissions. The socket is the credential. There is no token and no handshake (INV-08).

The line format

The protocol is one JSON object on one line, in both directions. The version is compared, not negotiated. A different version is a named refusal.

A request carries exactly one of intent, read, or watch. Two at once is a refusal. A read is wall or scene. A watch is the projection, then one line for each change.

The round trip is the identity: from_wire(&to_wire(intent)) == intent for every variant. A test holds that rule. The CLI builds the same JSON. Without the rule, the two halves of the wire could drift apart.

The authority and the viewer

A fleet has one authority. A viewer asks the authority for a Scene and draws it. The role is a value: Role::Local is the wall, and Role::Remote(path) is a viewer. The code path is the same for both. The difference is which process applies a change.

The viewer uses pull, not push. It sends read: "scene" when its session is not busy. The answer carries a seq. If the seq has not moved, the viewer does one comparison and rebuilds nothing. A push channel is not needed here. A relay already holds a connection open for the phone.

The scene is the arrangement, not the pixels. It carries the workspaces, the panes, their cameras, their filters, and the fleet values. It does not carry a PNG. A viewer computes the picture from the same values that the authority used.

A viewer is not a second wall

If a viewer cannot reach its authority, it says so in one line and draws its own default wall. It does not invent the authority's state. A screen that refuses to draw because a socket is absent is worse than a screen that draws and says why.

The relay and the phone

The wall does not listen on TCP. A phone in another room cannot use the unix socket. The wall dials out to a relay. The phone also talks to the relay. The relay joins the two connections.

The relay frames have five names. The wall sends hello first, with its own Minos credential. The relay answers welcome. A request from a phone carries device: the device key. An answer back to a phone carries to.

A device key is 32 fresh bytes. The wall stores only the SHA-256 hash in devices.toml. A revoked device stops at its next frame. A frame from a key that no row holds gets one answer: that device is not paired. The one exception is pair.claim. A phone that has never paired has no key to send, so that one verb can come before a name.

What the wall remembers

The wall writes four files. Each file has one owner and one job. No file holds a secret except the credential file, and that file is mode 0600.

config.tomlthe deploymentMinos URLs, camera start, stale threshold, credential pathby a human
credentials.tomlthe deploymentone refresh token, or an identifier and passwordby a human; mode 0600
layout.tomlthe operatorworkspaces, panes, cameras, names, filters, tree and newsroom positionsby the wall, 1.5 s after the arrangement stops

devices.tomlthe wallpaired device names and key hasheson pair and on forget

layout.toml holds the arrangement and nothing else. deny_unknown_fields is what keeps it that way. A hand-written key that the wall does not know is refused, not ignored. A camera is written with six decimals. A split ratio is clamped to 0.05 through 0.95. A file that the wall cannot read is a log line and the default wall, not a failed start.

Nothing is saved that is not an arrangement. The selected hull, the open card, and the headlines are answers the wall has read. A wall that came back showing yesterday's answer as if it were today's would be lying. The filter is the exception, and it is deliberate. A filter is a question, and a pane that hid the bases yesterday asked to hide them until told otherwise.

A capture writes nothing

State.headless guards every writer. A scene never reads or writes layout.toml, settings.toml, or devices.toml. A golden must not depend on the machine that rendered it (INV-11).

The desk, and the one write to Minos

The desk is a second binary in the same workspace. It reads the picture. It writes relayed fixes for a batch of units. The route is POST /live-feed/fixes/relayed.

The desk has two parts that need no window. identity mints and keeps this installation's device id. time answers what a typed time will do. The screen is built from field, batch, report, and ui. A scene fixes the clock and the samples, so a desk capture is reproducible in the same way as a wall capture.

The desk uses the wall's projection and the wall's comparison function. It does not own a second map projection or a second golden comparison. A named scene in the desk is a desk scene. The wall does not know its name.

The desk writes. The wall does not.

A wall account has read actions and nothing else. The desk account has the action for the relayed route. Do not give the wall a write action to make a demo easier.
